# Testing guide

How we test Alethia, what each layer is for, and how to run and write tests. We follow the
**Testing Trophy** — the model best suited to a full-stack app whose business logic lives in
server actions over a database (vs the classic pyramid, which assumes a logic-heavy monolith).

```
            ┌───────────────────────┐
            │        E2E            │  few — only critical user journeys (Playwright)
          ┌─┴───────────────────────┴─┐
          │      Integration          │  the bulk — server actions + real-Postgres
          │   (actions, SQL, RLS)     │  queries/RLS; highest confidence per test
        ┌─┴───────────────────────────┴─┐
        │           Unit               │  pure logic — fast, deterministic, no I/O
      ┌─┴───────────────────────────────┴─┐
      │      Static analysis              │  tsc --noEmit + Biome/ESLint (already gating)
      └───────────────────────────────────┘
```

Why the trophy and not the pyramid: most of our logic is orchestration over Postgres + Stripe
+ auth. A test that exercises a real query or a whole server action catches far more than a
hundred mocked unit tests, so **integration is the widest band**. E2E stays deliberately small
(slow, flaky-prone) and covers only journeys a user would notice breaking.

## Layers at a glance

| Layer | Runner | Lives in | Mocks? | Runs in CI |
|---|---|---|---|---|
| **Static** | `tsc`, Biome/ESLint | whole repo | — | yes (gate) |
| **Unit** | Vitest (jsdom) | `apps/console/tests/{lib,validations}/**` | no I/O at all | yes |
| **Component** | Vitest + React Testing Library | `apps/console/tests/components/**` | server actions mocked | yes |
| **Action (mocked)** | Vitest | `apps/console/tests/actions/**` | DB/Stripe/auth mocked at the module boundary | yes |
| **Integration (real DB)** | Vitest (`vitest.integration.config.ts`) | `apps/console/tests/integration/**` | real Postgres, nothing else | gated (needs Postgres) |
| **Shared package** | Vitest | `packages/<pkg>/tests/**` (e.g. `@repo/ui`, `@repo/plan-catalog`) | per-package | yes (turbo fan-out) |
| **E2E** | Playwright | `apps/console/e2e/**` | real app, dev stack | **two projects** — see below |
| **Go** | `go test ./...` | `apps/{cli,runner}`, `packages/core` | `httptest` | yes (matrix) |

## Running tests

```bash
# Every project's test suite, with coverage (the CI gate; fans out via turbo).
pnpm exec turbo run test

# A single project (console app, or a shared package)
pnpm -F console test
pnpm -F @repo/ui test
pnpm -F @repo/plan-catalog test

# Same, watch mode, no coverage (fast feedback loop)
pnpm -F console test:watch

# Integration suite — needs Postgres up first
pnpm db:up                       # Postgres + migrations (from repo root)
pnpm -F console test:integration

# End-to-end (browser). One-time: install the Playwright browsers.
pnpm -F console exec playwright install chromium
# Needs the dev stack running (console on :3000, SES unconfigured so the OTP is logged):
pnpm dev:up
pnpm -F console test:e2e         # or test:e2e:ui for the Playwright UI

# Go
cd apps/runner && go test ./...
```

> **The legacy specs are gone.** Seven of them (`dashboard`, `sidebar`, `runners`, `jobs`,
> `design-project`, `addons-on-canvas`, `project-settings`) were deleted in #2875 rather than
> revalidated. They were not merely stale: each was structurally incapable of asserting anything.
> `dashboard` asserted a stat-card strip that CLAUDE.md §6 bans and that exists nowhere in the
> tree; `addons-on-canvas` asserted two strings were ABSENT from a route that does not exist, so
> it was vacuously true forever; `project-settings` skipped itself whenever the org had no
> project, and the fixture never creates one, so it could only ever report SKIPPED. A spec that
> cannot fail is worse than no spec, because it is counted as coverage.

## Coverage

- Generated by the unit run (`pnpm -F console test` → `vitest run --coverage`, v8 provider).
- Reports, written by that run into the console's gitignored coverage directory — so they exist
  only after you run it, which is why they are described here rather than linked: a terminal
  table, an index.html to browse locally, lcov.info, coverage-summary.json, and
  coverage-final.json — the raw statement map the ratchet reads.
- Scope: our business **logic** — `lib/**` + `app/server/actions/**` (generated migrations/seeds
  and tests excluded; see `vitest.config.ts`). Presentational `components/**` are deliberately
  **not** counted here — UI is covered by the focused `@repo/ui` component tests + e2e, so the
  badge reflects "is our logic tested" rather than being dragged down by untested view code.
- **Self-hosted badge (no third-party service):** the `coverage-badge` CI job (push-to-main)
  runs the suites, merges the per-project `coverage-summary.json` line totals via
  `scripts/coverage-badge.mjs`, and publishes the result to the orphan **`badges`** branch —
  the shields.io endpoint the README badge reads. Regenerate locally with
  `pnpm exec turbo run test && node scripts/coverage-badge.mjs`.

  **The badge JSON is deliberately not checked in.** It used to be, and the checked-in copy said
  91% while the published one said 67.8%. It could not be otherwise: this job runs only on push
  to `main` and publishes to `badges`, so it never writes a number back into the tree, and
  nothing reconciled the two. The number now lives only where it is measured. (A push to `main`
  cannot be made directly — `protect-main` is `enforcement: active` with `bypass_actors: []`,
  which is why the badge goes to an orphan branch rather than to `main`.)
- **Thresholds are report-only today and ratcheted up as suites land.** When a layer is
  meaningfully covered, raise the floor in `vitest.config.ts → test.coverage.thresholds` so it
  can't regress.

### What the two badges actually count (be honest)

| Badge | Counts | Does **not** count |
|---|---|---|
| **coverage** | every project in `scripts/ts-coverage-sweep.json`: console **logic** (`lib/**`, `app/server/actions/**`), `@repo/ui` src, `@repo/plan-catalog`, `@repo/format`, `apps/marketing`'s logic surface, and `ee` (the licensed tier) | console `components/**` (presentational), the docs/blog apps, `@repo/{email,brand}` |
| **go coverage** | aggregate of `apps/cli` + `apps/runner` + `packages/core` (`go test -coverprofile`, via `scripts/go-coverage-badge.mjs`) | — |

That first row named three projects for as long as `scripts/coverage-badge.mjs` did — while the
record listed six and the badge's "could not read that project" branch merely warned. So the
published number described half the repository and looked exactly like a number that described
all of it. Both now read the record, and a project the badge cannot read is an error that names it.

They climb as more logic gets tested, and neither is cherry-picked *upward* by discarding a
failing suite. But "honest" was too strong a word for the **coverage** badge, and it is being
earned rather than asserted under #2649:

- The console scope excludes ~7,300 lines of `lib/**` and `app/server/actions/**` on top of the
  `components/**` exclusion above — some of it correctly (real-SQL modules verified by the
  integration tier), some of it under reasons that have since expired.
- `@repo/ui` counts an **allowlist** of hand-listed files rather than its whole `src/`. An
  include-allowlist is an exclusion with the sign flipped and no comment.

`apps/console` is the first project recorded: **`apps/console/coverage-exclusions.yaml`** carries
one entry per exclusion, and `pnpm check:coverage-exclusions` re-reads it on every PR. The section
is the decision — `infrastructural:` (not product code, and the path must match a declared class),
`tier_separation:` (proven by a named test suite) or `baseline:` (real debt, with an owning issue
and a verified `state:`, shrink-only). **Adding an exclusion without a manifest entry fails, and so
does a manifest entry whose exclusion has gone.**

What the guard checks about a `tier_separation:` claim is a **value import**: it resolves the named
suite's imports the way vitest resolves them and requires one for the module and for each name in
`symbols:`. `import type { X }`, `import { type X }`, `typeof import("…")` and a `vi.mock` of the
module are all non-evidence — the first three are erased by the compiler and the fourth replaces the
module, so v8 records nothing either way. It does not step into a function body, so an export that
is imported and never called satisfies the claim.

`symbols:` is also checked for **completeness**: every runtime export of an excluded file must be
accounted for, in `symbols:` or in `baseline:`. A list of two of a module's seven exports reads
exactly like a list of all seven.

Three projects are not yet enrolled and are recorded as such rather than left silent — `@repo/ui`
(48 files hidden behind a hand-listed `include`), `apps/marketing` and `ee` (six `exclude:` entries
between them, none manifested). Each carries a **`coverage-exclusions.pending`** marker naming the
issue that will delete it: `issue: #1234`, plus an optional one-line `reason:`. The guard derives
the pending set from those markers rather than from a list of its own, names and counts them on
every run, and fails if one is missing, unreadable, or left behind once its project is enrolled.
Enrolling them is the next unit.

That first pass already retired one false claim: the console config said
`tests/integration/reconcile-b2c.test.ts` verifies `lib/reconcile/gc.ts`, and that suite never
imports it (#3262).

Until every one of those is recorded as a decision with checkable evidence, read the coverage
badge as "the measured part of our logic is this well tested", not "our logic is this well
tested". The **go coverage** badge has no such caveat: every package in all four modules is
floored and ratcheted by `scripts/go-coverage.sh`.

Regenerate the Go badge locally with: `for m in apps/cli apps/runner packages/core; do (cd $m && go test -coverprofile=cover.out ./...); done && node scripts/go-coverage-badge.mjs`.

## Writing tests — recipes

### Unit (pure logic)
No mocks, no I/O. Import the function and assert. Pass any "now"/clock as an argument so tests
are deterministic. Model: `tests/lib/billing/usage.test.ts`, `tests/filters/range.test.ts`.

```ts
import { describe, expect, it } from "vitest";
import { resolvePlanEntitlements } from "@/lib/billing/plan";

it("falls back to community when the subscription isn't live", () => {
  expect(resolvePlanEntitlements("team", "canceled").organizations).toBe(false);
});
```

### Action (mocked boundary)
Mock the I/O modules — DB, Stripe, auth — and assert the action's orchestration and branching.
Pattern: `tests/lib/cli/providers.test.ts` (uses `vi.mock`).

```ts
vi.mock("@/lib/authz/guard", () => ({ currentActor: vi.fn() }));
vi.mock("@/lib/billing/queries", () => ({ getOrgBilling: vi.fn() }));
// ...arrange the mocks, call the action, assert it returned/branched correctly.
```

### Integration (real Postgres)
Lives in `tests/integration/**` and runs via `vitest.integration.config.ts`. Use the shared
`tests/integration/setup.ts` to get a migrated, isolated database; seed rows; call the real
query builder; assert the SQL result. This is the only layer that verifies SQL, the day-bucket
/ clamp math, and **RLS isolation** (one org can't read another's rows).

### Component (RTL)
Render with `@testing-library/react`, drive with `@testing-library/user-event`, mock the
server actions the component imports. Form components: reuse
`tests/components/design-project/test-utils.tsx` (`renderWithForm`).

### E2E (Playwright)
Keep them few and high-value. Auth goes through the real email-OTP flow — the shared fixture
in `e2e/fixtures/auth.ts` requests a code and reads it from the dev server log. Gate anything
needing Stripe behind `test.skip(!process.env.STRIPE_SECRET_KEY)`.

**Which projects CI actually runs — check before citing "covered by e2e".**
`playwright.config.ts` defines eight project entries; `.github/workflows/ci.yml` launches
**two** of them on every PR:

| project | runs in CI | job |
|---|:---:|---|
| `setup` | yes (dependency) | both, via `auth.setup.ts` |
| `hero` | **yes** | `E2E (browser · Playwright hero path)` |
| `elench-ai` | **yes** | `E2E (browser · Elench AI journeys · scripted model)` |
| `elench-ux` | **yes** | folded into `E2E (browser · Elench AI journeys · scripted model)` (#2875) |
| `elench-live` | nightly | `e2e-ai-nightly.yml` |
| `canvas`, `console`, `qa` | **no** — local only, and now LABELLED as such | — |

`qa` alone matches all 24 `e2e/flows/*.spec.ts` (~320 tests). So "this is covered by e2e" is only
true of the projects marked yes above — everything else is a local-only suite, and an exclusion
justified by a project CI never launches is justified by nothing.

**`chromium` is gone, and it was the mechanism.** It was a DENYLIST over the whole `testDir`, so
every newly added spec fell into it automatically — and since no workflow ever invoked it, every
new spec was born dead. That is why four projects, not one, had drifted out of CI. It is now an
allowlist, and `assertNoDeadZone()` runs at config load *inside both required jobs* and fails when
a spec is selected by no project, a project has no declared run-posture, or a posture disagrees
with what the workflows actually invoke — the last two read `.github/workflows/**` rather than
restating a belief about it. The per-project table now lives in `apps/console/e2e/README.md`.

Both CI jobs also still guard that the project matches at least one test, because a `--project`
whose `testMatch` selects zero specs exits 0.

## Test organization — the standard (one rule, no drift)

**The owning workspace project owns its tests, in its own `tests/` directory.** `turbo run
test` fans out across every project that defines a `test` script, and the `coverage-badge` job
merges each project's `coverage-summary.json` into one public number — the same fan-out model
the repo already uses for `lint`/`check-types`.

- **Each project has a `tests/` dir** + a `test` script: `apps/console`, `packages/ui`,
  `packages/plan-catalog`, and any future package. A package's logic and **its tests live
  together** — e.g. `@repo/ui/range` and the filter components are tested in
  `packages/ui/tests/`, not from the console.
- **Tests go in `tests/`, never co-located in `src/`.** For `@repo/ui` a `src/*.test.tsx` would
  be matched by its `"./*": "./src/*.tsx"` export glob and scanned by the apps' Tailwind
  `@source packages/ui/src` + `transpilePackages` — polluting exports/build. A package-level
  `tests/` dir avoids this and keeps the rule uniform with the app.
- **Within a project, mirror the source path** under `tests/` (`lib/billing/plan.ts` →
  `tests/lib/billing/plan.test.ts`; `@repo/ui/src/range.ts` → `packages/ui/tests/range.test.ts`).
- **Naming:** `*.test.ts(x)` = Vitest; `*.spec.ts` = Playwright e2e (`apps/console/e2e/**`).
  The real-DB integration tests are gated by directory (`apps/console/tests/integration/**`) +
  their own config.
- **Go** stays co-located `*_test.go` (the language idiom).

There are **no inline tests next to app source** and no "half here, half there" — every TS test
lives under a `tests/` directory of its owning project.

## Conventions

- One behavior per `it`; name it as the expectation ("rejects a taken slug").
- Deterministic: inject clocks/ids; never assert on `Date.now()` or random output directly.
- Every new pure module ships with a test in the same PR, in its project's `tests/` (mirroring
  the source path).
