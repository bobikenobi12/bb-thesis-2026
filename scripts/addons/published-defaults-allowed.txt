# Values an add-on ships that its upstream chart ALSO publishes.
#
# One `<addon>.<secret data key>` per line. See scripts/addons/check-published-defaults.sh.
#
# THIS LIST IS A RATCHET. The check fails when an entry stops appearing, so a fix cannot land
# without also shrinking the list — and an entry marked IN FLIGHT below will fail here the moment
# its PR merges, which is the intended way to be reminded.
#
# Two kinds of entry, and the distinction is the whole point of the file:

# ── NOT CREDENTIALS ─────────────────────────────────────────────────────────────────────────────
# Public by nature. Nothing leaks by matching the chart's default.

harbor.redisURL
# `redis://addon-harbor-redis:6379/5?idle_timeout_seconds=30` — an in-cluster service address with
# no credential in it. It matches the chart default because the DNS name is derived from the release
# name, which is deterministic by design.

# ── REAL CREDENTIALS, NOT YET FIXABLE ───────────────────────────────────────────────────────────

harbor.POSTGRESQL_PASSWORD
harbor.POSTGRES_PASSWORD
# `changeit`, harbor's INTERNAL database. The chart exposes an `existingSecret` for the EXTERNAL
# database only; the internal one takes a plain value, so setting it would put the credential into
# Helm values and therefore into `config_snapshot`, which is Postgres-persisted — the A0.0 leak the
# W4.5 design exists to prevent. A default password reachable only from inside the namespace is the
# lesser problem. Fixing it properly needs an upstream chart change. See #2848.

# harbor.REGISTRY_CREDENTIAL_PASSWORD left this list on 2026-08-27 (#2823). The dependency decision
# it was waiting on resolved to `bcryptjs`: docker distribution's htpasswd access controller takes
# bcrypt only, so minting REGISTRY_PASSWD alongside its REGISTRY_HTPASSWD needed a hasher the
# workspace did not have. With `registry.credentials.existingSecret` wired, the chart no longer
# renders its published `harbor_registry_password` at all.

# ══ THE HETZNER DATA-SERVICE SPECS ══════════════════════════════════════════════════════════════
#
# `hetzner-services.ts` renders nine more charts — the in-cluster carriers for the database, cache,
# queue, registry, secret, topic and nosql node KINDS — and this check had never seen any of them
# (#3299). Harbor is rendered from BOTH sources, and #2846's fix went to the marketplace copy only.
# These entries are what covering the second fixture found on its first run.

# ── NOT CREDENTIALS ─────────────────────────────────────────────────────────────────────────────

hetzner-service.registry-app-images.redisURL
# The same in-cluster service address as `harbor.redisURL` above, one release name along. No
# credential in it, and it matches by construction because the DNS name derives from the release.

hetzner-service.topic-events.default.json
# `{"url": "nats://addon-topic-events-nats"}` — the nats-box CLI's context file. An in-cluster
# address with no credential, and NATS is deployed without authentication here (the `topic` node is
# reachable only from inside the cluster), so there is nothing for the context to carry.
#
# It appears at all only because this scan now reads `stringData:` as well as `data:`. The NATS
# chart renders its only Secret as stringData, so before that it was reported as
# "EXTRACTION BROKE — the render contains Secret documents but none decoded" and the chart went
# UNCHECKED. The extraction-broke comment already named a stringData block as a cause; NATS is the
# first chart to have hit it.

# ── REAL CREDENTIALS, NOT YET FIXABLE ───────────────────────────────────────────────────────────

hetzner-service.registry-app-images.POSTGRESQL_PASSWORD
hetzner-service.registry-app-images.POSTGRES_PASSWORD
# `changeit`, harbor's INTERNAL database — the same constant, the same chart, the same reason as
# `harbor.POSTGRES*` above: the chart exposes `existingSecret` for the EXTERNAL database only, so
# setting it would put the credential into Helm values and therefore into `config_snapshot`. #2848.
