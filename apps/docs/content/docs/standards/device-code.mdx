# Device Authorization Grant

## What the standard is

The **OAuth 2.0 Device Authorization Grant** ([RFC 8628](https://www.rfc-editor.org/rfc/rfc8628))
authenticates a client that cannot easily host a browser or receive a redirect — a CLI, a TV, an IoT
device. The device asks the authorization server for a **device code** plus a human-readable
**user code**, tells the user to open a **verification URI** and enter the code, then **polls** a
token endpoint until the user approves (`authorization_pending` / `slow_down`) or the code expires.
The user authenticates in a full browser on another device; the CLI never handles their password.

## How Alethia implements it

`alethia login` (and the guided `alethia init`) run a browser-approval flow in this spirit, with a
couple of deliberate deviations from the literal RFC — documented below so the behaviour is
auditable. The CLI code lives in `apps/cli/cmd/login.go`; the control-plane routes are under
`apps/console/app/api/auth/cli/`.

<Steps>

### Start
`alethia login` generates a `device_code` (a client-side **UUID**, `uuid.New()`) and a `user_code`
(eight characters from an unambiguous consonant alphabet, printed to the terminal).

### Register the request
The CLI `POST`s both codes, its own name and version to `/api/auth/cli/start`. The route records a
pending `cli_logins` row carrying the `user_code`, the requesting IP, the `user-agent`, and a
deadline for the **decision** window. The insert never overwrites an existing row, because the route
is unauthenticated by necessity — the terminal has no session yet.

Registration is best-effort on the client: against a control plane that predates the route the CLI
prints a warning and continues, and the browser then shows less about the request.

### Read the request in the browser
The CLI opens `${web-origin}/cli/login?device_code=<uuid>&user_code=<code>`. The page
(`apps/console/app/(private)/cli/login/page.tsx`) requires an authenticated Better Auth session and
shows the `user_code` from the link.

`GET /api/auth/cli/request` answers with the account that approval would bind, what approval hands
over, who is asking, and how long is left — every field from the registration rather than from the
link, so nothing it returns is under the sender's control except the codes, which must match what
was registered.

<Callout type="warn">
  **The page does not read that route yet.** The endpoint and the columns behind it ship ahead of
  the screen that displays them; the richer consent screen is the page rebuild tracked in #3889 and
  #3631. Until then the browser shows the `user_code` and a generic prompt, and this section
  describes the route's contract rather than what a user currently sees.
</Callout>

### Approve in the browser
The page `POST`s to `/api/auth/cli/generate`. That route binds the `device_code` to
`session.user.id`, and best-effort stashes the user's first linked git provider token (held
transiently in `verification_code`). It refuses a `device_code` that belongs to another account, one
that was already refused, and a `user_code` that disagrees with the registered one.

### Or refuse it
"This isn't me" `POST`s to `/api/auth/cli/deny`, which is session-gated and rate-limited exactly like
`generate` — an unauthenticated version would let anyone terminate someone else's in-flight login.
The route writes a `denied_at` marker, clears the bound account and anything stashed for it, and the
refusal is terminal: the same link cannot be approved afterwards.

### Poll to exchange
The CLI polls `POST /api/auth/cli/exchange` with `{ device_code }` every 2 seconds. A **404** means
"pending" (`pollForToken` keeps waiting), a **403** carrying `access_denied` means the user refused
and the poll stops, a **429** means back off and keep waiting, and any other non-2xx is fatal. The
claiming delete is narrowed to approved, unrefused rows, so polling neither consumes the pending row
the browser is reading from nor erases a refusal.

### Mint and store
Once the row shows a `profile_id`, `exchange` **deletes the record** (single use) and mints two JWTs
with the `jose` library, signed HS256 with `CLI_JWT_SECRET`:

- `access_token` — `type: "access"`, **1 hour** TTL.
- `refresh_token` — `type: "refresh"`, **90 day** TTL.

Both are written to `~/.config/alethia/credentials.json` (`os.UserConfigDir()/alethia/credentials.json`,
mode `0755` dir). The git provider token rides back as `provider_token`.

### Refresh
Before each authed call, `getAuthTokenInternal` (`apps/cli/cmd/auth_utils.go`) parses the access
token's `exp`; if it is within 1 minute of expiry it calls `POST /api/auth/cli/refresh` with the
refresh token, which verifies `type === "refresh"` and issues a fresh 1-hour access token. When the
refresh token is gone or invalid, the CLI re-runs the browser flow.

</Steps>

<Callout type="warn">
  **Deviations from RFC 8628 (be precise).** Alethia's flow is *modeled on* the device grant but is
  not a literal implementation:
  <br />• The `user_code` is **compared, not typed**. The CLI mints it, registers it, and prints it;
  the browser URL carries both codes and approval is a click. The user's job is to check that the code
  on screen is the one their terminal printed — the server refuses any other.
  <br />• Both codes are **minted by the client**, not issued by the authorization server. The server
  binds the pair at registration and refuses a mismatch from then on.
  <br />• Pending status is signalled with **HTTP 404**, not the RFC's `authorization_pending` /
  `slow_down` token-endpoint errors; the poll interval is a fixed 2s. A refusal does use the RFC's
  `access_denied`, over HTTP 403.
  <br />• The CLI tokens are **HS256 JWTs** with placeholder `iss`/`aud` (`urn:example:issuer` /
  `urn:example:audience`), distinct from the Better Auth web session. See [JWT / JWS](/standards/jose).
</Callout>
