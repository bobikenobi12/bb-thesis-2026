# Verify Commands

Every `PLAN` and `DEPLOY` job carries an **elench evidence receipt**: the per-control verification
report, sealed to the hash of the exact OpenTofu plan that was applied, and signed with ed25519.
The `verify` group reads that receipt from the terminal.

`alethia verify receipt` checks the signature and **exits non-zero when it cannot**, so you can gate
a deployment pipeline on it. `alethia verify show` prints the report behind the verdict.

<Callout type="info">
The CLI is a client of the same Console API. Both commands call `/cli/jobs/<id>` with your
[CLI token](/cli/authentication) and operate on the **active organization**
(`alethia org switch`).
</Callout>

## Choosing the job

Both commands act on one job. The id is optional, and there are three ways to say which job you
mean:

```bash
alethia verify receipt 8f3c2a1e-4b7d-4c2a-9f1e-2d3c4b5a6978  # an id you already have
alethia verify receipt --latest       # the most recent PLAN or DEPLOY — no id needed
alethia verify receipt                # a picker, on a terminal
```

`--latest` is the one to use in a script: it needs no terminal, so it works under `--no-input`.
Narrow it until it names one job.

| Flag | Description |
|------|-------------|
| `--latest` | Act on the most recent matching job instead of naming one. Works with `--no-input`. |
| `--type` | Narrow to a job type — see [Jobs Commands](/cli/commands/jobs) for the full set. |
| `--status` | Narrow to a job status. |
| `--project` | Narrow to a project, by name or by an id prefix. |
| `--job`, `-j` | The job id, as a flag. The same thing as passing it as an argument. |

Only `PLAN` and `DEPLOY` jobs carry a receipt, so `--latest` and the picker consider **only those
two types** — otherwise the newest job in a busy org is usually a scheduled `DETECT_DRIFT` that
`verify` can do nothing with. Naming a `--type` yourself overrides that, and an id on the command
line is always taken as given.

The receipt is written when the run **finishes**, and `--latest` narrows by type, not by
completion. `alethia project plan` returns as soon as the job is queued unless you passed `-w`, so
the newest `PLAN` is often one that is still running — `verify` says so, and says what to do about
it. Add `--status SUCCESS` to take the newest job that has already finished:

```bash
alethia verify receipt --latest --status SUCCESS
```

The search covers the 50 most recent jobs, newest first. A `--type` or `--status` value outside the
enum is refused, and the message lists the values that exist.

Two combinations are refused rather than guessed:

- An id **and** `--latest`. Both name a job, so obeying one would make the other a lie.
- An id **and** a narrowing flag. `verify show <the id> --type DEPLOY` on a `PLAN` job would print
  the plan's report and look as though it had filtered.

When the CLI picked the job for you, it names which one on **stderr** before the output starts, so
`alethia verify show --latest -o json > report.json` still writes only the report.

## `alethia verify receipt`

Fetch a job's receipt and verify it.

```bash
alethia verify receipt --latest
alethia verify receipt 4f3c2b1a-9d6e-4a3b-8c17-5e2f1a9b7c04 -o json
alethia verify receipt --latest --key-file alethia-receipts.pub
```

| Flag | Required | Description |
|------|----------|-------------|
| `--key` | No | Verify against this base64 ed25519 public key instead of the trusted set. |
| `--key-file` | No | Same, read from a file. |
| `--allow-unsigned` | No | Exit zero when the receipt carries no signature. |
| `--allow-untrusted` | No | Exit zero when the signature is self-consistent but its key is not vouched for. |

Plus the selector flags from [Choosing the job](#choosing-the-job).

```
alethia · verify receipt
  Signature        ✓ signature verified against your organization's own recorded key
  Trust            org
  Algorithm        ed25519
  Key ID           9f2c4a1b7e5d3068
  Verdict          pass
  Sealed to plan   3b1f...c204
  Control catalog  elench-controls-0.5.2
  Evaluated        9 Mar 2026, 15:04
  Controls         14 pass, 0 fail, 0 warn, 0 n/a
```

The glyph on the `Signature` row has **three** states, not two:

| Glyph | Meaning |
|---|---|
| `✓` | verified against a key that is vouched for, or the one you pinned |
| `◐` | the signature is self-consistent, but who signed it is **unestablished** |
| `✗` | there is no signature, or it does not match the receipt |

`◐` is the forged-receipt shape, and it exits non-zero unless you pass `--allow-untrusted`. The
`Trust` and reason rows below it carry the full answer either way.

### What a green check means

The signature is verified against a key **the control plane vouches for** — your organization's own
recorded signing key, or the Alethia platform key — fetched from `GET /cli/signing-keys`.

This matters more than it looks. A receipt carries the public key it was signed with, so it will
always verify against *itself*, whoever produced it. Checking only that proves the document was not
altered in transit; it does not prove Alethia signed it. Binding the receipt's `key_id` to a
separately-served trusted key is what makes the difference, and a receipt signed by a key outside
that set fails — which is exactly what a forged receipt looks like.

The `Trust` field names the answer:

| Trust | Meaning |
|---|---|
| `pinned` | verified against the key you supplied with `--key`/`--key-file` |
| `org` | verified against your organization's own recorded signing key |
| `platform` | verified against the Alethia platform key — attests "Alethia asserted this" |
| `self` | only the receipt's own embedded key verified; who signed it is unestablished |

For verification that depends on nothing the control plane says about itself — the posture an
auditor or a security reviewer will want — pass the public key out of band with `--key-file`.

### Exit status

Exit status is part of the contract, so this can gate a pipeline:

| Situation | Exit |
|---|---|
| Signature verified against a vouched-for or pinned key | `0` |
| The job carries no receipt | non-zero |
| The receipt is unsigned (`algorithm: "none"`) | non-zero, or `0` with `--allow-unsigned` |
| The signature does not match the receipt | non-zero — **always**, no flag forgives it |
| The signature is valid but its key is not vouched for | non-zero, or `0` with `--allow-untrusted` |

A receipt that fails its own signature check has been altered since it was signed. No flag
downgrades that.

Receipts are unsigned when the runner had no `ALETHIA_RECEIPT_SIGNING_KEY` configured. That is a
legitimate state and the receipt still renders — but it is not evidence, so it fails by default.

## `alethia verify show`

Print the per-control report the receipt seals.

```bash
alethia verify show --latest
alethia verify show 4f3c2b1a-9d6e-4a3b-8c17-5e2f1a9b7c04 -o json
```

The selector flags from [Choosing the job](#choosing-the-job) are the only ones this command takes.

```
Verify: pass (aws, catalog elench-controls-0.5.2) — 14 pass, 0 fail, 0 warn, 1 not evaluable

Control        Status         Severity  Title
KEYLESS-001    pass           high      No static cloud credentials
LEASTPRIV-001  pass           high      No wildcard admin policy
OIDC-001       not_evaluable  medium    OIDC trust is scoped

▸ OIDC-001 — OIDC trust is scoped
    coverage: no OIDC provider in the plan
```

Controls reporting `not_evaluable` are shown, never hidden. A control the engine could not inspect
is not a control that passed, and a report that quietly dropped them would overstate what was
checked. Any recorded waiver prints with who granted it, why, and when it expires.

`verify show` exits non-zero on a blocking verdict, matching `elench-verify`.

Add `-o json` for the full report object; `-o csv` emits the control rows.
