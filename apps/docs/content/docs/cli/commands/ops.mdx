# Ops Commands

The `ops` group is the terminal-first **break-glass** surface: privileged incident-recovery
actions for on-call operators. Every verb hits the same audited `/api/breakglass/*` endpoints as
the operator UI, with the same bearer [CLI token](/cli/authentication) and the same append-only
audit trail.

<Callout type="warn">
The entire surface is gated behind the `ALETHIA_BREAKGLASS_ENABLED` flag **and** the
`BREAKGLASS_OPERATORS` server-side allowlist. A non-operator — or a deployment that has not enabled
break-glass — is refused with a 403/404. Membership in an organization is **not** the wall: these
endpoints are cross-tenant and bypass row-level security, so the operator allowlist is the only gate.
</Callout>

## The break-glass model

Four rules hold for every action.

- **Audited.** An append-only audit record is written *before* the act. Every verb requires a
  `--reason` of at least eight characters, and it is what the next person reading the audit has to
  go on.
- **Typed-confirm.** A mutating action echoes the exact resource id back to the server; a mismatch
  is refused. The CLI sends this confirmation for you.
- **Confirmed at the terminal.** Every action that changes something names the resource and the
  consequence and waits for you. `--yes` opts in ahead of time, which is what a runbook or a
  pipeline passes. With prompts unavailable and no `--yes`, the command exits non-zero having
  changed nothing — it never exits `0` having done nothing.
- **Two-person approval for high-blast actions.** `force-release-lock`, `state-surgery`, and
  `orphan-clean` require an `--approval` token minted by a **different** operator through
  [`alethia ops approve`](#alethia-ops-approve). The server enforces that the approver and the actor
  are different people.

Each action opens a fresh time-boxed break-glass session before it runs, records the reason, then
executes against the single audited execute endpoint. The session opens **after** you confirm, so a
declined action leaves no trace.

## Nothing is copied between commands

Every id in this group is an optional positional or an optional flag. Give one and it is passed
through exactly as typed, with no listing request made for it. Give none on a terminal and the
command asks:

- `inspect-job`, `retry-job` and `cancel-job` offer your organization's recent jobs, rendered by
  the [`jobs`](/cli/commands/jobs) group's own line renderer so a job reads the same in both.
- `drain-runner` and `restart-runner` offer every runner, including the offline ones — a drain is
  aimed at the runner that is wrong.
- `unstick-env` offers a project, then its environments, and starts the compare-and-swap
  precondition at the status the environment is actually in.
- `orphan-detect` and `orphan-clean` offer your projects.
- `approve` offers the actions that take an approval, read from the same catalog the server
  enforces.

The one value you still type from elsewhere is `--approval`, and that is the point of it: a
two-person token is minted by another operator on another terminal and handed to you. A token this
CLI could fetch for you would not be two-person.

A state key and a Stripe event id have no listing anywhere, so those two are asked as questions
rather than offered as menus.

## Blast radius

Each verb is labelled with its blast radius in its help text. The labels come from the server's
break-glass catalog, so they are the same ones the dispatcher enforces.

| Blast | Verbs | Confirms |
|-------|-------|----------|
| none (read-only) | `inspect-job`, `orphan-detect` | no — nothing changes |
| low | `retry-job`, `cancel-job`, `drain-runner`, `replay-webhook` | yes |
| medium | `unstick-env`, `restart-runner` | yes |
| HIGH (two-person) | `force-release-lock`, `state-surgery`, `orphan-clean` | yes, plus `--approval` |

## `alethia ops`

The group itself is runnable and prints the verb list with each one's blast radius, which is the
fastest way to see what break-glass can do without reading this page.

```bash
alethia ops
```

It takes no flags and performs no action — listing the surface is not itself a privileged act, so
it needs neither a `--reason` nor an audit record.

## `alethia ops session`

Open a standalone time-boxed break-glass session. The action verbs open their own session; this is
for inspecting or warming a session, or for scripts that reuse one.

```bash
alethia ops session --reason incident-1234-triage
```

{/* fieldspec: alethia ops session */}

| Field | What it is | Set without the form |
| --- | --- | --- |
| Reason | Why you are breaking glass; it is written to the immutable audit before the act | `--reason` |

Prints the session id, the resolved operator, and the session's expiry.

## `alethia ops approve`

Mint a single-use, TTL'd, two-person approval bound to a high-blast action and resource. Run this as
the **second** operator; the acting operator then passes the printed id as `--approval`.

```bash
alethia ops approve --reason incident-1234-signoff
alethia ops approve state_surgery projects/acme/prod.tfstate --reason incident-1234-signoff
```

{/* fieldspec: alethia ops approve */}

| Field | What it is | Set without the form |
| --- | --- | --- |
| Action | Which high-blast action this approval lets the other operator perform | `[action]` |
| Resource | The exact resource the approval is bound to; a different one is refused | `[resource-id]` |
| Reason | Why you are breaking glass; it is written to the immutable audit before the act | `--reason` |

The action must be one that takes an approval: `force_release_state_lock`, `state_surgery`, or
`orphan_clean`. The server answers `400` for any other one, so the CLI refuses it first and names
the three.

Prints the approval id, the action and resource it is bound to, the approver, and its expiry.

## `alethia ops inspect-job`

Read a job's full row cross-tenant. Read-only (blast: none), so it asks for no confirmation and
carries no `--yes`.

```bash
alethia ops inspect-job --reason incident-1234-deploy-hung
alethia ops inspect-job 8f3c2a1b-77de-4c05-9a41-2b8e6a1d40f7 --reason incident-1234-deploy-hung
```

{/* fieldspec: alethia ops inspect-job */}

| Field | What it is | Set without the form |
| --- | --- | --- |
| Job | The job to read; pick one, or pass an id an alert gave you | `[job-id]` |
| Reason | Why you are breaking glass; it is written to the immutable audit before the act | `--reason` |

The picker lists your own organization's recent jobs. Break-glass reaches jobs that listing does
not, which is why an id given on the command line skips it entirely.

## `alethia ops retry-job`

| Reason | Why you are breaking glass; it is written to the immutable audit before the act | `--reason` |

## `alethia ops unstick-env`

Move a stuck environment to a target status through the `set_env_status` compare-and-swap primitive —
never a raw `UPDATE` (blast: medium). A compare-and-swap miss is refused, which is what makes this
safe to run against an environment that is moving under you.

```bash
alethia ops unstick-env --reason incident-1234-stuck-after-crash
alethia ops unstick-env 5c1f0a92-3d77-4a10-b8e2-7f9d4c6b1a03 --from PROVISIONING,QUEUED --to FAILED --reason incident-1234-stuck-after-crash --yes
```

{/* fieldspec: alethia ops unstick-env */}

| Field | What it is | Set without the form |
| --- | --- | --- |
| Environment | The environment to move; pick one, or pass its id | `[environment-id]` |
| Expected from | The statuses the move is allowed to start from; a compare-and-swap miss is refused | `--from` |
| Move to | The status to move the environment to | `--to` |
| Reason | Why you are breaking glass; it is written to the immutable audit before the act | `--reason` |

Both sides are project statuses: `DRAFT`, `QUEUED`, `PROVISIONING`, `ACTIVE`, `FAILED`,
`DESTROYING`, `DESTROYED`. Anything else is refused before the request is made, because the server
refuses it too.

Picked from the list, `--from` starts at the status the environment is in. Given an id on the
command line the CLI has not looked the environment up, so `--from` is required — inventing a
precondition is the one thing a compare-and-swap exists to prevent.

## `alethia ops force-release-lock`

Force-release a stranded [OpenTofu](/concepts/glossary) state lock (blast: HIGH, two-person). It
rotates the fencing token and bumps the generation — never a naive delete — so a writer still
holding the lock is fenced out mid-apply.

```bash
alethia ops force-release-lock projects/acme/prod.tfstate --approval 6b21d8f4-0c5e-4a93-9f27-3d81b6e5c704 --reason incident-1234-runner-died-holding-lock --yes
```

{/* fieldspec: alethia ops force-release-lock */}

| Field | What it is | Set without the form |
| --- | --- | --- |
| State key | The locked state object; the fencing token rotates so a zombie writer is fenced out | `[state-key]` |
| Approval | The approval id a second operator read out to you from their own ops approve run | `--approval` |
| Reason | Why you are breaking glass; it is written to the immutable audit before the act | `--reason` |

## `alethia ops state-surgery`

Queue a privileged `STATE_SURGERY` job through the normal Runner/state pipeline, with fencing intact
(blast: HIGH, two-person).

```bash
alethia ops state-surgery projects/acme/prod.tfstate --approval 6b21d8f4-0c5e-4a93-9f27-3d81b6e5c704 --note import-orphaned-rds --reason incident-1234-failed-apply --yes
```

{/* fieldspec: alethia ops state-surgery */}

| Field | What it is | Set without the form |
| --- | --- | --- |
| State key | The state object the surgery job will operate on | `[state-key]` |
| Approval | The approval id a second operator read out to you from their own ops approve run | `--approval` |
| Repair note | What the repair is meant to do; recorded in the audit and read by whoever reviews it | `--note` |
| Reason | Why you are breaking glass; it is written to the immutable audit before the act | `--reason` |

The note is the only optional field in the group. It is still asked for on a terminal, because the
person who reads the audit is not the person running this, and "state surgery, no note" is the row
that gets escalated.

<Callout type="info">
The runner-side executor ships **inert** (fail-closed): the queued job fails cleanly without
mutating state. See the `STATE_SURGERY` job type in [Job Commands](/cli/commands/jobs).
</Callout>

## `alethia ops replay-webhook`

Re-dispatch a stored Stripe webhook event through the same idempotent handler the live webhook uses
(blast: low).

```bash
alethia ops replay-webhook --reason incident-1234-missed-invoice
alethia ops replay-webhook evt_1P9xKjLkdIwHu7ix --reason incident-1234-missed-invoice --yes
alethia ops replay-webhook evt_1P9xKjLkdIwHu7ix --send-emails --reason incident-1234-missed-invoice --yes
```

{/* fieldspec: alethia ops replay-webhook */}

| Field | What it is | Set without the form |
| --- | --- | --- |
| Stripe event | The stored event to re-dispatch through the live idempotent handler | `[stripe-event-id]` |
| Re-send emails | Branded emails are the one non-idempotent side effect, so they are suppressed unless you ask | `--send-emails` |
| Reason | Why you are breaking glass; it is written to the immutable audit before the act | `--reason` |

The confirmation says which of the two it is about to do. The handler is idempotent; the emails are
not, so the run that re-sends them is named as such.

## Scripting the group

Every field above is settable from the command line, so the whole group works with `--no-input`.
The rule is one line: **a value you did not supply is asked for, and if it cannot be asked for the
command tells you which flag or positional would have answered it, and exits non-zero.** The one
exception is `state-surgery`'s `--note`, which is optional: an unattended run gets no note rather
than a refusal.

Two things a script needs to know:

- `--yes` is required on every mutating verb when prompts are unavailable. Without it the command
  exits non-zero and changes nothing, which is the safe answer for a pipeline that reached a
  destructive verb it did not mean to.
- `-o json` prints the payload alone. The styled success line is only rendered for the table
  format, so a break-glass result pipes into `jq` without a sentence in front of it.

  <Callout type="warn">
  One thing still writes to `stdout` ahead of the payload: the loading spinner, which draws its
  frames there rather than on `stderr`. A redirected or piped `-o json` result can therefore begin
  with terminal escape sequences, and `jq` reports `Invalid numeric literal at line 1, column 2`.
  Until [#3838](https://github.com/alethialabs-io/alethialabs/issues/3838) lands, parse from the
  first `{` or `[` rather than from byte zero. This affects every command with a spinner, not only
  `ops`.
  </Callout>

```bash
alethia ops inspect-job 8f3c2a1b-77de-4c05-9a41-2b8e6a1d40f7 --reason incident-1234-triage --no-input -o json
```
