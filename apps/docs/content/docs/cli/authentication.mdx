# Authentication

alethia authenticates two ways, for two different callers:

- **You, at a terminal** — the **Device Authorization Grant** (RFC 8628). You never type a password.
- **A pipeline** — a **service-account token**, supplied through `$ALETHIA_TOKEN`. No browser, no prompt.

For the full technical details, see [Authentication Flows](/concepts/authentication).

## Login

```bash
alethia login
```

<Steps>

### CLI generates two codes
A UUID `device_code` identifying this login attempt, and a short `user_code` printed to your terminal.

### CLI registers the request
It sends both codes, its own name and version to `POST /api/auth/cli/start`. Console stores them with the
IP and browser agent it saw, so the approval page can tell you who is asking.

### Browser opens
Navigates to `{console_url}/cli/login?device_code={code}&user_code={user_code}`.

### Approve in browser
Sign in with any OAuth provider (GitHub, GitLab, Bitbucket, Google) or email OTP. The page names the
account that is about to be bound, what approval hands over, who is asking and how long is left. Check
that the code on screen is the one your terminal printed, then approve — nothing is typed back into the
terminal.

### CLI polls for the token
While you approve in the browser, the CLI shows a spinner and polls `POST /api/auth/cli/exchange` with the
`device_code`. Console returns HTTP 404 while pending; once approved it returns a JWT pair (access + refresh).

### Tokens stored
Saved to `~/.config/alethia/credentials.json`.

</Steps>

## Refusing a login you did not start

If the code on screen is not the one your terminal printed, or you did not run `alethia login` at all,
press **This isn't me**.

That records the refusal in Console rather than only in the browser. Three things follow:

- The device that is polling is told at once, with the standard `access_denied` error, instead of waiting
  out its own timeout.
- Nothing is handed over — no access token, no refresh token, and none of your linked git provider's
  OAuth token.
- The refusal is final for that link. Opening it again cannot approve it; a genuine sign-in needs a fresh
  `alethia login`.

### Force Re-authentication

```bash
alethia login --force
```

Re-authenticates even if a valid token already exists. Useful when switching accounts.

## Logout

```bash
alethia logout
```

Removes `~/.config/alethia/credentials.json`.

## Token Lifecycle

| Token | TTL | Purpose |
|-------|-----|---------|
| Access token | 1 hour | `Authorization: Bearer` header on API calls |
| Refresh token | 90 days | Obtain new access tokens transparently |

Before each API call, alethia decodes the access token's `exp` claim. If it has expired (or expires within a minute), the CLI refreshes automatically via `POST /api/auth/cli/refresh` and rewrites the stored access token. The user never notices.

## Identity & Active Org

After logging in, confirm who you are signed in as and which organization the CLI is scoped to:

```bash
alethia whoami   # user, active org, role, plan, default runner
alethia config   # control-plane URL, active org, on-disk file paths
```

The active organization is sent as the `X-Alethia-Org` header on every request. Set or change it
with `alethia org switch`. See [Identity & Global Options](/cli/identity) and
[Organizations, Members & Teams](/cli/commands/organizations).

## Running in CI

The device flow needs a browser and a person, so a pipeline cannot use it. Mint a **service-account
token** instead:

```bash
alethia token create --name "github-actions"
```

The token is printed **once**, on stdout, with everything else on stderr — so you can pipe it
straight into a secret store without selecting it by eye:

```bash
alethia token create --name "github-actions" | gh secret set ALETHIA_TOKEN
```

Then set `ALETHIA_TOKEN` in your job and use the CLI normally. Nothing is written to disk, and no
`alethia login` is needed:

```yaml
- name: Deploy staging
  env:
    ALETHIA_TOKEN: ${{ secrets.ALETHIA_TOKEN }}
  run: |
    alethia project apply --env staging --wait --no-input
```

Pair it with `--no-input`, which makes the CLI fail rather than prompt — together they mean a job
never hangs waiting for an answer nobody is there to give.

### What a service token can do

A token **acts as the person who created it**, inside the **one organization** it was minted for.
That org is fixed when the token is created: an `X-Alethia-Org` header that disagrees with it is
refused, not ignored, so a token issued for one organization can never act on another.

It also stops working the moment its creator leaves that organization — membership is re-checked on
every request, not trusted from when the token was minted.

### Minting a token

Run `alethia token create` on a terminal with no flags and it asks for the two things it needs:

{/* fieldspec: alethia token create */}

| Field | What it is | Set without the form |
| --- | --- | --- |
| Name | What this token is for, so a list of tokens is a list of purposes | `--name` |
| Expires | A token that never expires is a credential nobody remembers to rotate | `--expires-in-days` |

The flags are the complete contract: anything the form can ask, a flag can set, so
`--no-input` never needs a prompt.

```bash
alethia token create                              # asks for the name and the lifetime
alethia token create --name ci --expires-in-days 90   # the same, unattended
```

`--expires-in-days 0` — the default — never expires. That is a deliberate choice rather than an
oversight, and it is why the form asks: a credential with no end date is one nobody remembers to
rotate.

### Managing tokens

```bash
alethia token list     # id, name, prefix, created, expires, last used, status
alethia token revoke   # pick from the live tokens, or pass an id
```

`alethia token list` shows `last used: never` for a token nothing has ever presented. That is usually
the most interesting row on the list — a credential that was minted, put somewhere, and forgotten.

`alethia token revoke` with no argument shows the tokens that are still live and revokes the one you
pick, so you never have to copy an opaque id out of `token list` by eye. Already-revoked tokens are
left out of the picker; revoking one again does nothing.

{/* fieldspec: alethia token revoke */}

| Field | What it is | Set without the form |
| --- | --- | --- |
| Token | The token to revoke; it stops working on its very next request | `[id]` |

```bash
alethia token revoke                                           # pick from a list
alethia token revoke 3f2b9c14-7a1e-4d68-9c05-2b8e6a1d40f7    # revoke a known id, no prompt
```

<Callout type="info">
Revoke carries **no `--yes`**, unlike every other destructive command. Its asymmetry runs the other
way: revoking a token you did not mean to costs one `alethia token create`, while failing to revoke a
leaked one costs the organization. A confirmation here would fail an incident-response pipeline and
leave the credential live.
</Callout>

<Callout type="warn">
The token value is shown **once** and is never stored — the server keeps only a hash of it. If you
lose it, revoke it and mint another. There is no way to read it back, by design.
</Callout>

Minting, listing and revoking tokens requires the `org:manage_tokens` permission, which **owners and
admins** hold. Operators deliberately do not: issuing a credential that carries someone's access into
an unattended pipeline is a higher bar than deploying infrastructure by hand.

## Environment Variables

| Variable | Default | Purpose |
|----------|---------|---------|
| `ALETHIA_WEB_ORIGIN` | Production URL (baked at build) | Override the Alethia API URL |
| `ALETHIA_TOKEN` | unset | A service-account token for non-interactive use. When set, the CLI uses it and never reads or writes the credentials file. |

```bash
export ALETHIA_WEB_ORIGIN=http://localhost:3000
alethia login  # authenticates against local dev server
```

The `--token` flag does the same thing as `$ALETHIA_TOKEN` and takes precedence over it. Prefer the
environment variable in CI: a flag value lands in the process table and in shell history, where an
environment variable does not.

## Token Storage

```
~/.config/alethia/credentials.json
```

```json
{
  "access_token": "eyJ...",
  "refresh_token": "eyJ...",
  "user_email": "you@example.com"
}
```

The access-token expiry is read from the JWT itself (the `exp` claim), so no separate timestamp is
stored. The active-org context is kept separately in `~/.config/alethia/config.json` (see
[Configuration](/cli/configuration)).

<Callout type="warn">
This file contains authentication tokens. It is not encrypted — protect it with filesystem permissions.
</Callout>
