# Configuration

alethia stores configuration and credentials under the OS user-config directory (`~/.config/alethia`
on Linux, `~/Library/Application Support/alethia` on macOS — the location follows Go's
`os.UserConfigDir`). Inspect the resolved values and on-disk paths at any time with
[`alethia config`](#alethia-config).

## File Locations

| File | Purpose |
|------|---------|
| `~/.config/alethia/credentials.json` | CLI authentication tokens (access + refresh JWT) |
| `~/.config/alethia/config.json` | Active organization context (id, name, slug) |

## credentials.json

Created by `alethia login`. Contains JWT tokens for API authentication:

```json
{
  "access_token": "eyJ...",
  "refresh_token": "eyJ...",
  "user_email": "you@example.com"
}
```

The access token is refreshed automatically before each API call if expired. See [Authentication](/cli/authentication).

## config.json

Created/updated by `alethia org switch`. Records the active organization, which is sent as the
`X-Alethia-Org` header on every request:

```json
{
  "active_org_id": "org_123",
  "active_org_name": "Acme",
  "active_org_slug": "acme"
}
```

Clear it with `alethia config clear-context`.

## `alethia config`

Show the resolved CLI configuration: the control-plane URL (`ALETHIA_WEB_ORIGIN`), the active
organization context, and the on-disk paths of the credentials and config files.

```bash
alethia config
```

```
Field          Value
web origin     https://app.alethialabs.io (config)
active org     Acme
active org id  org_123
credentials    /Users/you/Library/Application Support/alethia/credentials.json
config         /Users/you/Library/Application Support/alethia/config.json
```

`alethia config clear-context` clears the active organization context. `alethia config -o json`
emits the same values as a JSON object.

## Config keys

These are the keys `alethia config get` reads. `alethia config set` writes the ones marked
`config set`; a key set anywhere else says which command owns it, because a value you can read and
cannot write needs to tell you what does write it.

{/* configkeys */}

| Key | What it is | How to set it |
| --- | --- | --- |
| `web-origin` | The control-plane URL the CLI talks to (hosted, self-hosted or dev). | `config set` |
| `active-org` | The organization every request is scoped to, sent as X-Alethia-Org. | `alethia org switch` |

`active-org` is deliberately read-only. Setting it by name would have to resolve that name to an id
and a slug — which is a server round-trip, and that round-trip is `alethia org switch`. A
`config set active-org` that wrote only the name would leave the id stale and scope every subsequent
request to the *previous* organization.

The underscore spellings (`web_origin`, `active_org`) are accepted too, because that is how the keys
appear in `config.json` and people type what they have read.

## `alethia config set`

```bash
alethia config set                                       # pick the key, edit the current value
alethia config set web-origin https://alethia.internal.example.com   # the same, unattended
```

Run with no arguments on a terminal, `config set` asks for both:

{/* fieldspec: alethia config set */}

| Field | What it is | Set without the form |
| --- | --- | --- |
| Config key | Which value to change | `[key]` |
| Value | The new value; the form describes it with the chosen key's own summary | `[value]` |

The value field is pre-filled with the **stored** value, so the form is an edit rather than a
re-type, and it is validated by the same rule `config set` applies — a value the form accepts is
never refused a moment later. It shows what is stored rather than what is in effect, because that
is what the write replaces: if `ALETHIA_WEB_ORIGIN` is set, the form says so and still seeds the
file's value, so pressing Enter cannot overwrite it with the environment's.

With `--no-input` both arguments are required; the command fails rather than guessing.

<Callout type="info">
`ALETHIA_WEB_ORIGIN` **outranks** the config file. If it is set to a different URL,
`alethia config set web-origin` says so after saving, because otherwise the write appears to succeed
and every subsequent command keeps talking to the environment's origin.
</Callout>

`alethia config get` prints the bare value in the default table format — so
`$(alethia config get web-origin)` works — and key/value pairs under `-o json` or `-o csv`.

An unset key, such as `active-org` before you have picked an organization, prints as `—` in the
table and as an empty string under `-o json` and `-o csv`. The dash is for a person reading a
column; a script tests the machine formats for emptiness.

## `alethia config export`

Export an environment's **design document** — the same nested shape the console design form holds,
and the one [`alethia project design apply`](/cli/commands/project) accepts. By default the content is
written to stdout; pass `--out` to write it to a file, or `-o json` to get the export envelope
(content + filename + format).

```bash
# Print the design document to stdout
alethia config export my-project

# Round-trip it: export, edit, apply
alethia config export my-project --out my-project.json
alethia project design apply -p my-project -f my-project.json --dry-run
alethia project design apply -p my-project -f my-project.json
```

| Flag | Default | Description |
|------|---------|-------------|
| `--format` | `json` | The content format. `json` is the only supported value. |
| `--out` | _(stdout)_ | Write the content to this file instead of stdout. |

The project name is optional — omit it in an interactive terminal to pick one from a list. Backing
call: `GET /cli/configurations/by-project-name/<name>/export`.

<Callout type="warn">
  **Before 0.5.x this command did not work at all.** The route it calls did not exist, so every
  invocation 404'd, and its default `--format legacy-yaml` named a format nothing in the product has
  ever produced. If you pinned `--format legacy-yaml`, drop it or pass `json`; the server now refuses
  that value by name rather than returning JSON labelled as YAML.
</Callout>

## Runner Credentials

The `alethia` CLI does not store Runner credentials. A self-operated Runner is a
separate binary configured entirely through environment variables — register the
Runner in the console (or via the API) to obtain a `runner_id` / `runner_token`,
then set `ALETHIA_RUNNER_ID` and `ALETHIA_RUNNER_TOKEN` on the host. See
[Self-Operated Runners](/runner/self-hosted) for the full env contract.

## Environment Variables

| Variable | Default | Purpose |
|----------|---------|---------|
| `ALETHIA_WEB_ORIGIN` | `https://alethialabs.io` (compiled-in default) | Override the Alethia API base URL |
| `ALETHIA_NO_UPDATE_CHECK` | unset | Disable the daily interactive new-release notice |

These are the CLI configuration environment variables. Runner processes use a separate runtime
environment documented with the runner deployment method.

## Global Flags

Four persistent flags are available on every command:

| Flag | Default | Description |
|------|---------|-------------|
| `-o, --output <table\|json\|csv>` | `table` | Output format. `json`/`csv` print static, machine-readable output, and never open an interactive table. |
| `--no-input` | off | Disable interactive prompts; fail instead of prompting. Auto-enabled when stdin is not a terminal. A form is refused separately when the stream it would draw on is redirected, so `alethia … 2> log` still renders the rich table. |
| `--token <token>` | unset | Service-account token for non-interactive use. Prefer the `ALETHIA_TOKEN` environment variable in CI: a flag value lands in the process table and in shell history. |
| `--org <id>` | the active org | Organization to act in for this invocation, instead of the active one. Sent as the `X-Alethia-Org` header on every request, and used as the org in the request path of `members` and `teams`. It selects a scope rather than granting one: the control plane refuses it with `403` when you are not a member of that organization. Under a service token it must name the token's OWN organization — a different one is refused with `403`, never quietly ignored, so a pipeline cannot believe it is acting on one org while every write lands in another. |

See [Identity & Global Options](/cli/identity) for output-format examples and scripting tips.

## Control-Plane URL Resolution

The control-plane URL resolves in precedence order: the `ALETHIA_WEB_ORIGIN` environment
variable, then the persisted config (`alethia config set web-origin <url>`), then a compiled-in
default (`https://alethialabs.io`). The hosted default is a constant baked into the binary, so the
production build needs no configuration (GoReleaser's `ldflags` inject only the CLI version, not the
URL). For development or a self-hosted control plane, override it with the environment variable:

```bash
export ALETHIA_WEB_ORIGIN=http://localhost:3000
alethia login  # authenticates against local server
```
